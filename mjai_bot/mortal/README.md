# mortal-298k

Local wrapper running the strongest publicly downloadable riichi mahjong
model — [VoidShine/mortal-298k](https://huggingface.co/VoidShine/mortal-298k)
(Mortal v4, ResNet 192ch × 40 blocks, ~10.8M params, trained by deep RL on
2025–2026 Tenhou high-dan hanchan logs; MAKA benchmark average S+) — through
the **official** Mortal engine, so observation encoding, legal-action
masking and the agari guard all match upstream exactly.

- 4-player **hanchan** only (the checkpoint is hanchan; `supported_modes =
  ["4p"]`).
- CPU inference; measured on an i7-13700K: ~15-25 ms per decision driving
  `mortal.py` directly, ~80 ms through bot.py (probe overhead), ~1.3 s for
  the first decision after model load. Akagi's budget is 5 s.

## Layout

```
mjai_bot/mortal/
├── bot.py            # Akagi ↔ mortal.py protocol proxy (stdlib only)
├── manifest.toml     # bot metadata + engine path settings (empty defaults)
├── settings.toml     # machine-local engine paths (gitignored; UI-writable)
├── engine.toml       # config passed to mortal.py via MORTAL_CFG (auto-generated, gitignored)
├── mortal_298k.pth   # weights, downloaded from HuggingFace (AGPL-3.0, gitignored)
├── sim_game.py       # offline inference test: simulates one kyoku vs the bot
├── test_bot.py       # unit tests for the proxy (fake engine)
├── README.md         # this file
├── README.hf.md      # upstream model card
├── config.hf.toml    # upstream training config (for reference)
└── LICENSE           # AGPL-3.0 (from the HuggingFace repo)
```

Tracked here: the wrapper code, docs and the HF provenance files. Gitignored
(root `.gitignore`): the weights (AGPL binary, 130 MB), `engine.toml` and
`settings.toml` (machine-local absolute paths), `game_log.jsonl` (test
output).

## One-time setup (this machine)

1. Clone Mortal somewhere outside this repo and build its Python extension:

   ```
   git clone https://github.com/Equim-chan/Mortal ../mortal
   cd ../mortal
   uv venv -p 3.12 .venv
   uv pip install --python .venv/Scripts/python.exe torch numpy toml tqdm tensorboard maturin
   # PATH must contain cargo (rustup stable-msvc)
   cd libriichi
   ../.venv/Scripts/python.exe -m maturin build --release
   cp ../target/release/riichi.dll ../mortal/libriichi.pyd
   ```

   (maturin warns about a missing `PyInit_riichi` symbol — expected: the
   Cargo lib is named `riichi` but the Python module is `libriichi`. The
   DLL exports `PyInit_libriichi`; renaming it to `libriichi.pyd` next to
   `mortal.py` mirrors the upstream Dockerfile layout.)

2. Download the weights here:

   ```
   curl -L -o mortal_298k.pth \
     https://huggingface.co/VoidShine/mortal-298k/resolve/main/mortal_298k.pth
   ```

   Expected sha256:
   `bfb3a6c072aa0bfd4171a9cdc77cb6c02ae42cde920843f9e5784394f23447d8`
   (130,774,416 bytes)

3. Point the bot at your clone: set `python_path` and `mortal_dir` in the
   Bots tab (persisted to the gitignored `settings.toml`) or write
   `settings.toml` by hand:

   ```toml
   python_path = 'C:\...\mortal\.venv\Scripts\python.exe'
   mortal_dir  = 'C:\...\mortal\mortal'
   ```

   Standalone runs (`sim_game.py`, manual piping) read `settings.toml`
   directly; under Akagi the merged config arrives via `AKAGI_BOT_CONFIG`.

`engine.toml` is generated by `bot.py` on first run (`state_file` → the
local `mortal_298k.pth`); edit it by hand afterwards if needed — bot.py
never overwrites an existing file.

## Testing offline

```
python sim_game.py            # one kyoku, opponents tsumogiri, via bot.py
python sim_game.py --engine   # drive mortal.py directly (line protocol)
python test_bot.py            # proxy unit tests with a fake engine
```

## Protocol notes

Akagi sends one JSON **array** of mjai events per stdin line (batches,
flushed at decision points) and expects exactly one reaction per line.
`mortal.py` takes one **single** event per line and prints a reaction line
only at decision points (`libriichi.mjai.Bot.react` returns `None`
otherwise). `bot.py` reconciles the two: it forwards every event of a
batch individually, then answers with the last reaction collected —
waiting up to 4 s when the batch's last event opens a decision for our
seat (own tsumo, opponent dahai/kakan call window, own meld follow-up,
reach_accepted), or a 0.25 s grace window otherwise, falling back to
`{"type":"none"}`.

## License boundary

The AGPL-3.0 engine and weights stay inside their own process tree:
Akagi ↔ bot.py (this folder, repository code) ↔ mortal.py + torch
(engine venv, AGPL). They communicate only via stdin/stdout JSON lines,
so Akagi does not become a derived work of the model. Do not link
libriichi or import the weights from repository code.
